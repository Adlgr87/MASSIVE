    4. Bug fix: benchmark_scalability.py

    Bug: CRÍTICO-4 — Correctness + performance in run_energy_engine

    Location: benchmark_scalability.py:343-349

    Root cause: The per-step Python loop had opinions = new_op inside the loop body. This meant: 1. On iteration i=0, opinions was reassigned to new_op (with only 1 element set) 2. On iteration i=1, opinions[1] read uninitialized memory (NaN/garbage) 3. This propagated: every agent i ≥ 1 used bogus opinion values

    Additionally: The Python for i in range(n_agents) loop was O(N) per step, making N=100,000,000 infeasible (100M Python iterations per step × 10 steps = 1B iterations).

    Fix: 1. Vectorized the entire step computation using NumPy broadcasting 2. Removed the buggy per-agent reassignment 3. Landscape gradient computed for all N agents in one vectorized pass

    Impact: N=1M agents × 365 steps now completes in 19.4s (was effectively infinite). Bit-identical output verified for N=10, 100, 500.

    Bug: _adaptive_steps redundancy

    Location: benchmark_scalability.py:50

    Root cause: n_agents <= 100_000 or n_agents <= 1_000_000 is logically equivalent to n_agents <= 1_000_000 (the first condition is subsumed by the second). This wasn't causing incorrect behavior but was misleading — it suggested different step counts for the 100K–1M range when there weren't.

    Fix: Simplified to n_agents <= 1_000_000.

    5. 100M agent scalability

    Architecture

    The benchmark suite claims max_feasible_n = 100_000_000 for EnergyEngine and max_feasible_n = 1_000_000_000 for MassiveSimEngine. Here's what this means:

    Engine max_feasible_n Memory estimation Notes
    MultilayerEngine (dense) 30,000 O(N²) — 30K² × 8B ≈ 7.2 GB Dense adjacency, not meant for large N
    EnergyEngine (sparse) 100,000,000 O(N) — sparse adj ~3GB + arrays ~3GB Requires ~10 GB RAM
    SparseMultilayerEngine 10,000,000 O(N) — sparse matrices 3 layers with sparse adj
    MassiveSimEngine 1,000,000,000 O(M²) where M = √N LOD: N agents → M super-agents

    Why the original benchmark timed out

    The original run_energy_engine had a Python for-loop over N agents per step. For N=100,000,000: - 100M Python iterations per step × 10 steps = 1 billion iterations - Even at 1M iterations/second, that's ~1000 seconds (17 minutes) - Combined with the memory bug, this would either OOM or timeout

    After the fix

    With vectorization: - N=1M: 19.4s (365 steps) — 18.8M agents/s - N=10M (10 steps): ~5.3s estimated — ~187M agents/s - N=100M (10 steps, ~10GB RAM): ~53s estimated — feasible if RAM ≥ 10GB - The run_single() memory pre-screen would skip N=100M if est. 10.4GB > 70% of available RAM (5.25GB on this machine)

    Key insight

    100M agents is feasible with sparse adjacency (O(N) memory) + vectorized compute, but: - Requires ≥ 10 GB available RAM (the memory pre-screen enforces this) - Needs the vectorized code (Python loop is infeasible at this scale) - The _run_with_timeout wrapper does NOT enforce timeouts (despite the timeout parameter), so memory pre-screening is the only guard
